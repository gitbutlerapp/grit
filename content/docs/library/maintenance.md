---
title: Maintenance
summary: Object fsck validation and repository hooks.
---

Repository maintenance helpers live in [`maintenance`](rustdoc:grit_lib::maintenance):

- [`Repository::write_commit_graph`](rustdoc:grit_lib::repo::Repository) — atomic monolithic `objects/info/commit-graph` with optional changed-path Bloom filters ([`CommitGraphOptions`](rustdoc:grit_lib::maintenance::CommitGraphOptions), [`CommitGraphWriteReport`](rustdoc:grit_lib::maintenance::CommitGraphWriteReport)). Shallow clones, `info/grafts` and enabled replace refs change commit parents, so no graph is written there and any existing one is deleted (Git ignores graphs in that state but `git fsck` still rejects them); [`CommitGraphWriteReport::skipped`](rustdoc:grit_lib::maintenance::CommitGraphWriteReport::skipped) holds the [`CommitGraphSkipReason`](rustdoc:grit_lib::maintenance::CommitGraphSkipReason).
- [`Repository::write_midx`](rustdoc:grit_lib::repo::Repository) — write `multi-pack-index` ([`MidxOptions`](rustdoc:grit_lib::maintenance::MidxOptions), [`MidxWriteReport`](rustdoc:grit_lib::maintenance::MidxWriteReport)). The file is format version 1 by default, readable by every Git with multi-pack-index support; `MidxOptions::version`, then `midx.version` in config, select version 2. Other values fail with [`MidxError::UnknownWriteVersion`](rustdoc:grit_lib::error::MidxError) before anything is written, including in dry-run mode. Incremental repack follows the same `midx.version` setting when it writes a multi-pack-index bitmap.
- [`References::pack`](rustdoc:grit_lib::refs::handle::References) — pack loose refs into `packed-refs` or compact reftable stacks ([`PackRefsOptions`](rustdoc:grit_lib::maintenance::PackRefsOptions)).
- [`repack_all`](rustdoc:grit_lib::maintenance::repack_all) and [`gc`](rustdoc:grit_lib::maintenance::gc) orchestrate repack and prune; [`repository_fsck::fsck`](rustdoc:grit_lib::maintenance::repository_fsck::fsck) validates the result.
- [`gc_auto`](rustdoc:grit_lib::maintenance::gc_auto) is `git gc --auto`: [`auto_gc_needed`](rustdoc:grit_lib::maintenance::auto_gc_needed) applies `gc.auto` (loose objects estimated from `objects/17`, two directory reads in total) and `gc.autoPackLimit` and returns an [`AutoGcReason`](rustdoc:grit_lib::maintenance::AutoGcReason). Too many loose objects packs the reachable ones into one new pack without touching existing packs (unreachable ones stay loose for `gc.pruneExpire`); too many packs runs a full consolidating gc. The result is an [`AutoGcOutcome`](rustdoc:grit_lib::maintenance::AutoGcOutcome) (not needed, already running, declined by the `pre-auto-gc` hook, or ran with [`GcStats`](rustdoc:grit_lib::maintenance::GcStats)). Call it after writing objects; the library never forks, so an application that honors `gc.autoDetach` ([`ConfigSet::gc_auto_detach`](rustdoc:grit_lib::config::ConfigSet::gc_auto_detach)) runs it on its own thread or process.
- [`gc`](rustdoc:grit_lib::maintenance::gc) and [`gc_auto`](rustdoc:grit_lib::maintenance::gc_auto) hold Git's `gc.pid` lock ([`GcLock`](rustdoc:grit_lib::maintenance::GcLock)) while they run, so maintenance never overlaps another grit or Git gc. A held lock is [`Error::MaintenanceRunning`](rustdoc:grit_lib::error::Error) from `gc` and [`AutoGcOutcome::AlreadyRunning`](rustdoc:grit_lib::maintenance::AutoGcOutcome) from `gc_auto`.

Maintenance APIs split into **repository fsck**, **object validation**, and **hook execution**:

- [`maintenance::repository_fsck`](rustdoc:grit_lib::maintenance::repository_fsck) — repository-wide integrity checks (loose/pack objects, connectivity from [`reachability_roots`](rustdoc:grit_lib::maintenance::repository_fsck::reachability_roots), dangling objects, refs, MIDX, commit-graph). Progress via [`ProgressSink`](rustdoc:grit_lib::progress::ProgressSink); severity follows Git defaults and `fsck.<msg-id>` config ([`issue_severity`](rustdoc:grit_lib::maintenance::repository_fsck::issue_severity)). Each [`FsckIssue`](rustdoc:grit_lib::maintenance::repository_fsck::FsckIssue) reports the object it concerns ([`FsckIssue::oid`](rustdoc:grit_lib::maintenance::repository_fsck::FsckIssue::oid)), the file or ref it was found in ([`FsckIssue::location`](rustdoc:grit_lib::maintenance::repository_fsck::FsckIssue::location)), and a one-line description ([`FsckIssue::detail`](rustdoc:grit_lib::maintenance::repository_fsck::FsckIssue::detail)), so callers can render findings without matching every variant.
  Packs are memory-mapped and verified in one depth-first pass over their delta trees on worker threads: each object is inflated once, hashed against its index entry and checked, then its bytes are dropped. Peak memory therefore follows the delta chains being walked plus a few dozen bytes per object (commit and tag links, object kinds), not the uncompressed size of the pack. A delta whose base is corrupt, missing or fails its hash check is reported as `corruptObject` along with every delta built on it. The connectivity walk re-reads trees from the object store, as Git does, instead of caching every tree entry.
- [`maintenance::fsck`](rustdoc:grit_lib::maintenance::fsck) — validate loose object bytes before hashing ([`fsck_object`](rustdoc:grit_lib::maintenance::fsck::fsck_object), [`FsckError`](rustdoc:grit_lib::maintenance::fsck::FsckError) with Git-compatible message ids). Connectivity walks for receive-pack and bundles live in [`maintenance::repository_fsck`](rustdoc:grit_lib::maintenance::repository_fsck).
- [`maintenance::repack`](rustdoc:grit_lib::maintenance::repack) — all-into-one repack using [`reachability_roots`](rustdoc:grit_lib::maintenance::repository_fsck::reachability_roots), optional `.rev`/`.bitmap` sidecars, pack pruning, and unreachable loose-object pruning via [`RepackOptions`](rustdoc:grit_lib::maintenance::RepackOptions) / [`RepackReport`](rustdoc:grit_lib::maintenance::RepackReport). [`Repository::repack`](rustdoc:grit_lib::repo::Repository) is a thin alias. Objects already in a pack keep their stored form (whole objects byte for byte, deltas with their base reference rewritten, chains capped at `pack.depth`); only loose objects and deltas whose base is dropped go through a streaming `pack.window` delta search, and the pack streams to disk. Set [`RepackOptions::force_recompress`](rustdoc:grit_lib::maintenance::RepackOptions) to recompute every delta, like `git repack -f`. Incremental repack (`RepackOptions::incremental`) keeps existing packs; when combined with `write_bitmap` and multiple packs, grit writes a multi-pack-index reachability bitmap instead of a single-pack sidecar.
- [`hooks`](rustdoc:grit_lib::command_runner::hooks) — resolve and run hook scripts through the repository [`CommandRunner`](rustdoc:grit_lib::command_runner::CommandRunner) ([`run_hook`](rustdoc:grit_lib::command_runner::hooks::run_hook), [`HookResult`](rustdoc:grit_lib::command_runner::hooks::HookResult)). A hook that runs and exits non-zero is `Ok(HookResult::Failed { status, output })` with its real exit status; a hook that cannot be started at all is [`HookError::Spawn`](rustdoc:grit_lib::command_runner::hooks::HookError) carrying the program, the `io::Error`, and whatever earlier hooks for the event (configured `hook.<name>.*` entries run first) already wrote. The library never prints hook output. By default ([`HookStdio::Capture`](rustdoc:grit_lib::command_runner::hooks::HookStdio)) both streams are piped and returned as a [`HookOutput`](rustdoc:grit_lib::command_runner::hooks::HookOutput) in the result, and in [`HookError::Failed`](rustdoc:grit_lib::command_runner::hooks::HookError) when [`HookResult::check`](rustdoc:grit_lib::command_runner::hooks::HookResult::check) or [`commit_worktree`](rustdoc:grit_lib::porcelain::commit::commit_worktree) turns a failing `pre-commit` or `commit-msg` into an error, so a TUI or GUI can show it in its own pane. The `Display` of the error stays one line. A terminal front end that wants Git's live output opens the repository with [`RepositoryOptions::with_hook_stdio`](rustdoc:grit_lib::config::environment::RepositoryOptions::with_hook_stdio)`(HookStdio::Inherit)`: the hook then writes straight to the process's stderr (its stdout too, except for `pre-push`) and the returned output is empty. Output an injected `CommandRunner` returns is only ever handed back, never re-emitted. Server-side hooks run by receive-pack are always captured and relayed to the client on the sideband. Scripts the OS refuses to execute run through `sh` (`/bin/sh` on Unix; on Windows the `#!` interpreter, resolved in the Git for Windows tree and then on the hook's `PATH`). A `post-commit` hook that cannot start never fails the commit; it is reported as [`Warning::HookNotRun`](rustdoc:grit_lib::diagnostics::Warning). The same holds for the hooks porcelain runs after an operation completes: [`switch_repository`](rustdoc:grit_lib::porcelain::switch::switch_repository) runs `post-checkout`, [`integrate_branch_with`](rustdoc:grit_lib::porcelain::merge::integrate_branch_with) runs `post-merge`, an amending [`create_commit`](rustdoc:grit_lib::porcelain::commit::create_commit) runs `post-rewrite amend`, and [`apply_rewrite`](rustdoc:grit_lib::revwalk::history::apply_rewrite) runs `post-checkout` and `post-rewrite rebase` (pairs from [`RewritePlan::rewritten_pairs`](rustdoc:grit_lib::revwalk::history::RewritePlan::rewritten_pairs)). Each takes a [`PostOperationHooks`](rustdoc:grit_lib::PostOperationHooks) option (`Skip` to opt out) and reports what ran as [`HookName`](rustdoc:grit_lib::HookName) values; [`run_post_checkout`](rustdoc:grit_lib::command_runner::hooks::run_post_checkout), [`run_post_merge`](rustdoc:grit_lib::command_runner::hooks::run_post_merge) and [`run_post_rewrite`](rustdoc:grit_lib::command_runner::hooks::run_post_rewrite) run one hook with Git's arguments. Hooks inherit every variable of the repository [`Environment`](rustdoc:grit_lib::config::environment::Environment) snapshot. [`Repository::hooks`](rustdoc:grit_lib::repo::Repository) lists scripts via [`RepositoryHooks::list`](rustdoc:grit_lib::repo_handles::RepositoryHooks) ([`HookInfo`](rustdoc:grit_lib::repo_handles::HookInfo), [`HookSource`](rustdoc:grit_lib::repo_handles::HookSource)). Tests often install [`RecordingRunner`](rustdoc:grit_lib::command_runner::RecordingRunner) via [`RepositoryOptions`](rustdoc:grit_lib::config::environment::RepositoryOptions).
- [`patch_ids`](rustdoc:grit_lib::diff::patch_ids) — [`Repository::patch_id`](rustdoc:grit_lib::repo::Repository) and [`compute_patch_id`](rustdoc:grit_lib::diff::patch_ids::compute_patch_id) for stable/unstable commit equivalence (merge commits return `None`). Text diffs use unified hunks with three context lines on each side, matching `git show --format= --no-ext-diff -U3 <REV> | git patch-id --stable` in stable mode. Nearby unchanged context is hashed; distant unchanged lines are excluded. [`compute_patch_id_for_paths`](rustdoc:grit_lib::diff::patch_ids::compute_patch_id_for_paths) applies the same rules to selected paths, while [`compute_patch_ids_from_text`](rustdoc:grit_lib::diff::patch_ids::compute_patch_ids_from_text) hashes the hunks supplied by its caller, including their chosen context.

The `grit` CLI maps fsck and hook failures to its own exit codes and messages; the library returns typed results only.
