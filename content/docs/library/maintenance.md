title: Maintenance
summary: Object fsck validation and repository hooks.
---

Repository maintenance helpers live in [`maintenance`](rustdoc:grit_lib::maintenance):

- [`Repository::write_commit_graph`](rustdoc:grit_lib::repo::Repository) — atomic monolithic `objects/info/commit-graph` with optional changed-path Bloom filters ([`CommitGraphOptions`](rustdoc:grit_lib::maintenance::CommitGraphOptions), [`CommitGraphWriteReport`](rustdoc:grit_lib::maintenance::CommitGraphWriteReport)). Shallow clones, `info/grafts` and enabled replace refs change commit parents, so no graph is written there and any existing one is deleted (Git ignores graphs in that state but `git fsck` still rejects them); [`CommitGraphWriteReport::skipped`](rustdoc:grit_lib::maintenance::CommitGraphWriteReport::skipped) holds the [`CommitGraphSkipReason`](rustdoc:grit_lib::maintenance::CommitGraphSkipReason). Writing needs the files backend; a repository with a custom primary store gets `Error::UnsupportedObjectStore`.
- [`build_commit_graph`](rustdoc:grit_lib::maintenance::build_commit_graph) (`Repository::build_commit_graph`) — the same graph built in memory through any object store, custom primaries included, returned as a [`CommitGraphBuild`](rustdoc:grit_lib::maintenance::CommitGraphBuild). The [`BuiltCommitGraph`](rustdoc:grit_lib::maintenance::BuiltCommitGraph) bytes match what `write_commit_graph` installs; a custom store keeps them itself and attaches them with `OdbBuilder::commit_graph` (see [Object stores](object-stores.md#commit-graphs-for-a-custom-store)).
- [`Repository::write_midx`](rustdoc:grit_lib::repo::Repository) — write `multi-pack-index` ([`MidxOptions`](rustdoc:grit_lib::maintenance::MidxOptions), [`MidxWriteReport`](rustdoc:grit_lib::maintenance::MidxWriteReport)). The file is format version 1 by default, readable by every Git with multi-pack-index support; `MidxOptions::version`, then `midx.version` in config, select version 2. Other values fail with [`MidxError::UnknownWriteVersion`](rustdoc:grit_lib::error::MidxError) before anything is written, including in dry-run mode. Incremental repack follows the same `midx.version` setting when it writes a multi-pack-index bitmap.
- [`References::pack`](rustdoc:grit_lib::refs::handle::References) — pack loose refs into `packed-refs` or compact reftable stacks ([`PackRefsOptions`](rustdoc:grit_lib::maintenance::PackRefsOptions)).
- [`repack_all`](rustdoc:grit_lib::maintenance::repack_all) and [`gc`](rustdoc:grit_lib::maintenance::gc) orchestrate repack and prune; [`repository_fsck::fsck`](rustdoc:grit_lib::maintenance::repository_fsck::fsck) validates the result.
- [`gc_auto`](rustdoc:grit_lib::maintenance::gc_auto) is `git gc --auto`: [`auto_gc_needed`](rustdoc:grit_lib::maintenance::auto_gc_needed) applies `gc.auto` (loose objects estimated from `objects/17`, two directory reads in total) and `gc.autoPackLimit` and returns an [`AutoGcReason`](rustdoc:grit_lib::maintenance::AutoGcReason). Too many loose objects packs the reachable ones into one new, self-contained pack without touching existing packs (unreachable ones stay loose for `gc.pruneExpire`), delta-compressed with `pack.window` / `pack.depth` like a full repack; too many packs runs a full consolidating gc. The result is an [`AutoGcOutcome`](rustdoc:grit_lib::maintenance::AutoGcOutcome) (not needed, already running, declined by the `pre-auto-gc` hook, or ran with [`GcStats`](rustdoc:grit_lib::maintenance::GcStats)). Call it after writing objects; the library never forks, so an application that honors `gc.autoDetach` ([`ConfigSet::gc_auto_detach`](rustdoc:grit_lib::config::ConfigSet::gc_auto_detach)) runs it on its own thread or process.
- [`gc`](rustdoc:grit_lib::maintenance::gc) and [`gc_auto`](rustdoc:grit_lib::maintenance::gc_auto) hold Git's `gc.pid` lock ([`GcLock`](rustdoc:grit_lib::maintenance::GcLock)) while they run, so maintenance never overlaps another grit or Git gc. A held lock is [`Error::MaintenanceRunning`](rustdoc:grit_lib::error::Error) from `gc` and [`AutoGcOutcome::AlreadyRunning`](rustdoc:grit_lib::maintenance::AutoGcOutcome) from `gc_auto`. During [`gc`](rustdoc:grit_lib::maintenance::gc), `gc.writeCommitGraph` and `core.commitGraph` gate commit-graph generation (existing graphs are kept when skipped), `gc.packRefs` gates pack-refs (`notbare` packs only when the repository has a work tree), and the last of `repack.writeBitmaps` / `pack.writeBitmaps` in config load order selects whether repack writes a bitmap (unset defaults to true on bare repos). Explicit [`write_commit_graph`](rustdoc:grit_lib::maintenance::write_commit_graph) and [`pack_refs`](rustdoc:grit_lib::maintenance::pack_refs) ignore the gc-only keys.

Maintenance APIs split into **repository fsck**, **object validation**, and **hook execution**:

- [`maintenance::repository_fsck`](rustdoc:grit_lib::maintenance::repository_fsck) — repository-wide integrity checks (loose/pack objects, connectivity from [`reachability_roots`](rustdoc:grit_lib::maintenance::repository_fsck::reachability_roots), dangling objects, refs, MIDX, commit-graph). Progress via [`ProgressSink`](rustdoc:grit_lib::progress::ProgressSink); severity follows Git defaults and `fsck.<msg-id>` config ([`issue_severity`](rustdoc:grit_lib::maintenance::repository_fsck::issue_severity)). Each [`FsckIssue`](rustdoc:grit_lib::maintenance::repository_fsck::FsckIssue) reports the object it concerns ([`FsckIssue::oid`](rustdoc:grit_lib::maintenance::repository_fsck::FsckIssue::oid)), the file or ref it was found in ([`FsckIssue::location`](rustdoc:grit_lib::maintenance::repository_fsck::FsckIssue::location)), and a one-line description ([`FsckIssue::detail`](rustdoc:grit_lib::maintenance::repository_fsck::FsckIssue::detail)), so callers can render findings without matching every variant.
  Packs are memory-mapped and verified in one depth-first pass over their delta trees on worker threads: each object is inflated once, hashed against its index entry and checked, then its bytes are dropped. Peak memory therefore follows the delta chains being walked plus a few dozen bytes per object (commit and tag links, object kinds), not the uncompressed size of the pack. A delta whose base is corrupt, missing or fails its hash check is reported as `corruptObject` along with every delta built on it. The connectivity walk re-reads trees from the object store, as Git does, instead of caching every tree entry.
- [`maintenance::fsck`](rustdoc:grit_lib::maintenance::fsck) — validate loose object bytes before hashing ([`fsck_object`](rustdoc:grit_lib::maintenance::fsck::fsck_object), [`FsckError`](rustdoc:grit_lib::maintenance::fsck::FsckError) with Git-compatible message ids). Connectivity walks for receive-pack and bundles live in [`maintenance::repository_fsck`](rustdoc:grit_lib::maintenance::repository_fsck).
- [`maintenance::repack`](rustdoc:grit_lib::maintenance::repack) — all-into-one repack using [`reachability_roots`](rustdoc:grit_lib::maintenance::repository_fsck::reachability_roots), optional `.rev`/`.bitmap` sidecars, pack pruning, and unreachable loose-object pruning via [`RepackOptions`](rustdoc:grit_lib::maintenance::RepackOptions) / [`RepackReport`](rustdoc:grit_lib::maintenance::RepackReport). [`Repository::repack`](rustdoc:grit_lib::repo::Repository) is a thin alias. Objects already in a pack keep their stored form (whole objects byte for byte, deltas with their base reference rewritten, chains capped at `pack.depth`); only loose objects and deltas whose base is dropped go through a streaming `pack.window` delta search, and the pack streams to disk. Set [`RepackOptions::force_recompress`](rustdoc:grit_lib::maintenance::RepackOptions) to recompute every delta, like `git repack -f`. Incremental repack (`RepackOptions::incremental`) keeps existing packs; when combined with `write_bitmap` and multiple packs, grit writes a multi-pack-index reachability bitmap instead of a single-pack sidecar.
- [`hooks`](rustdoc:grit_lib::command_runner::hooks) — resolve and run hook scripts through the repository [`CommandRunner`](rustdoc:grit_lib::command_runner::CommandRunner) ([`run_hook`](rustdoc:grit_lib::command_runner::hooks::run_hook), [`HookResult`](rustdoc:grit_lib::command_runner::hooks::HookResult)). A hook that runs and exits non-zero is `Ok(HookResult::Failed { status, output })` with its real exit status; a hook that cannot be started at all is [`HookError::Spawn`](rustdoc:grit_lib::command_runner::hooks::HookError) carrying the program, the `io::Error`, and whatever earlier hooks for the event (configured `hook.<name>.*` entries run first) already wrote. The library never prints hook output. By default ([`HookStdio::Capture`](rustdoc:grit_lib::command_runner::hooks::HookStdio)) both streams are piped and returned as a [`HookOutput`](rustdoc:grit_lib::command_runner::hooks::HookOutput) in the result, and in [`HookError::Failed`](rustdoc:grit_lib::command_runner::hooks::HookError) when [`HookResult::check`](rustdoc:grit_lib::command_runner::hooks::HookResult::check) or [`commit_worktree`](rustdoc:grit_lib::porcelain::commit::commit_worktree) turns a failing `pre-commit` or `commit-msg` into an error, so a TUI or GUI can show it in its own pane. The `Display` of the error stays one line. A terminal front end that wants Git's live output opens the repository with [`RepositoryOptions::with_hook_stdio`](rustdoc:grit_lib::config::environment::RepositoryOptions::with_hook_stdio)`(HookStdio::Inherit)`: the hook then writes straight to the process's stderr (its stdout too, except for `pre-push`) and the returned output is empty. Output an injected `CommandRunner` returns is only ever handed back, never re-emitted. Server-side hooks run by receive-pack are always captured and relayed to the client on the sideband. Scripts the OS refuses to execute run through `sh` (`/bin/sh` on Unix; on Windows the `#!` interpreter, resolved in the Git for Windows tree and then on the hook's `PATH`). A `post-commit` hook that cannot start never fails the commit; it is reported as [`Warning::HookNotRun`](rustdoc:grit_lib::diagnostics::Warning). The same holds for the hooks porcelain runs after an operation completes: [`switch_repository`](rustdoc:grit_lib::porcelain::switch::switch_repository) runs `post-checkout`, [`integrate_branch_with`](rustdoc:grit_lib::porcelain::merge::integrate_branch_with) runs `post-merge`, an amending [`create_commit`](rustdoc:grit_lib::porcelain::commit::create_commit) runs `post-rewrite amend`, and [`apply_rewrite`](rustdoc:grit_lib::revwalk::history::apply_rewrite) runs `post-checkout` and `post-rewrite rebase` (pairs from [`RewritePlan::rewritten_pairs`](rustdoc:grit_lib::revwalk::history::RewritePlan::rewritten_pairs)). Each takes a [`PostOperationHooks`](rustdoc:grit_lib::PostOperationHooks) option (`Skip` to opt out) and reports what ran as [`HookName`](rustdoc:grit_lib::HookName) values; [`run_post_checkout`](rustdoc:grit_lib::command_runner::hooks::run_post_checkout), [`run_post_merge`](rustdoc:grit_lib::command_runner::hooks::run_post_merge) and [`run_post_rewrite`](rustdoc:grit_lib::command_runner::hooks::run_post_rewrite) run one hook with Git's arguments. The hooks that run before an operation records anything can refuse it, with [`Error::Hook`](rustdoc:grit_lib::error::Error) wrapping [`HookError::Failed`](rustdoc:grit_lib::command_runner::hooks::HookError): [`create_commit`](rustdoc:grit_lib::porcelain::commit::create_commit) runs `pre-commit`, `prepare-commit-msg <COMMIT_EDITMSG> <source>` and `commit-msg`; [`integrate_branch_with`](rustdoc:grit_lib::porcelain::merge::integrate_branch_with) runs `pre-merge-commit`, then `prepare-commit-msg <MERGE_MSG> merge` and `commit-msg` with `MERGE_HEAD` recorded, and leaves the merge in progress when one refuses; [`start_rebase`](rustdoc:grit_lib::revwalk::history::start_rebase) runs `pre-rebase` as [`StartRebaseOptions::pre_rebase`](rustdoc:grit_lib::revwalk::history::StartRebaseOptions::pre_rebase) says, once the branch is known not to be up to date and before any commit is replayed, so a refusal comes before a replay conflict and writes nothing ([`plan_rebase_with_hook`](rustdoc:grit_lib::revwalk::history::plan_rebase_with_hook) does the same for callers that plan and apply a rebase themselves, [`run_pre_rebase`](rustdoc:grit_lib::command_runner::hooks::run_pre_rebase) runs the bare hook). [`HookPolicy::SkipVerify`](rustdoc:grit_lib::porcelain::commit::HookPolicy) ([`CommitRequest::hooks`](rustdoc:grit_lib::porcelain::commit::CommitRequest::hooks), [`MergeOptions::verify`](rustdoc:grit_lib::porcelain::merge::MergeOptions::verify)) is `--no-verify`: it skips `pre-commit`, `pre-merge-commit` and `commit-msg`, never `prepare-commit-msg`. Hooks inherit every variable of the repository [`Environment`](rustdoc:grit_lib::config::environment::Environment) snapshot. [`Repository::hooks`](rustdoc:grit_lib::repo::Repository) lists scripts via [`RepositoryHooks::list`](rustdoc:grit_lib::repo_handles::RepositoryHooks) ([`HookInfo`](rustdoc:grit_lib::repo_handles::HookInfo), [`HookSource`](rustdoc:grit_lib::repo_handles::HookSource)). Tests often install [`RecordingRunner`](rustdoc:grit_lib::command_runner::RecordingRunner) via [`RepositoryOptions`](rustdoc:grit_lib::config::environment::RepositoryOptions).
- [`patch_ids`](rustdoc:grit_lib::diff::patch_ids) — [`Repository::patch_id`](rustdoc:grit_lib::repo::Repository) and [`compute_patch_id`](rustdoc:grit_lib::diff::patch_ids::compute_patch_id) for stable/unstable commit equivalence (merge commits return `None`). Text diffs use unified hunks with three context lines on each side, matching `git show --format= --no-ext-diff -U3 <REV> | git patch-id --stable` in stable mode. Nearby unchanged context is hashed; distant unchanged lines are excluded. [`compute_patch_id_for_paths`](rustdoc:grit_lib::diff::patch_ids::compute_patch_id_for_paths) applies the same rules to selected paths, while [`compute_patch_ids_from_text`](rustdoc:grit_lib::diff::patch_ids::compute_patch_ids_from_text) hashes the hunks supplied by its caller, including their chosen context.
  [`Repository::patch_ids_for_revs`](rustdoc:grit_lib::repo::Repository) takes revision specs and expands ranges: `A..B` yields one `(patch_id, commit)` pair per commit in `rev-list` order, and `A...B` yields both sides as one unlabelled sequence. To compare the two sides of `A...B` (for example a branch before and after a force-push), set [`RevWalkListOptions::cherry_mark`](rustdoc:grit_lib::revwalk::RevWalkListOptions) and read [`RevListResult::cherry_matches`](rustdoc:grit_lib::revwalk::rev_list::RevListResult): each [`CherryMatch`](rustdoc:grit_lib::revwalk::rev_list::CherryMatch) lists the left and right commits sharing one patch-id, and for a one-to-one pair says whether the commit message changed.

[`offload_blobs`](rustdoc:grit_lib::maintenance::offload_blobs) moves large blobs from a repository to a large-object promisor (LOP), the way `git repack -a -d --filter=blob:limit=<n> --filter-to=<lop>` does in Git's own LOP tests. [`OffloadOptions`](rustdoc:grit_lib::maintenance::OffloadOptions) names the promisor remote and the filter: `blob:limit=<n>` selects blobs of at least `n` bytes, and the default is the remote's `partialCloneFilter`. The current time is passed in for the `gc.pid` lock. Nothing leaves the main repository before the LOP has it. Candidate blobs are copied into one new LOP pack, whole, and its `.keep` marker ([`IngestPackOptions::keep_message`](rustdoc:grit_lib::objects::index_pack::IngestPackOptions::keep_message)) is written before the pack appears, so a gc on the LOP cannot prune the unreferenced blobs. Only a copy the LOP itself holds in a `.keep` pack counts as already there: a loose or unkept copy may be pruned by the LOP's `gc`, and one reached through the LOP's alternates is not the LOP's, so those candidates are copied too. Every candidate is then checked to be in a `.keep` pack of the LOP, and the new pack is flushed to disk. Next `remote.<name>.promisor` is set (and `partialCloneFilter`, when the filter was given), along with `repack.writeBitmaps = false`, without which `git gc` fails on the repository once something is pushed. Finally the main repository's packs and loose objects are rewritten into one `.promisor` pack without the candidates, and that pack is flushed to disk before the old packs go. That rewrite keeps unreachable objects and leaves `.keep` packs alone. It deletes only the packs it listed when it started, so a concurrent push survives. Blobs a worktree's index or `HEAD` needs, and blobs in `.keep` packs, stay. The [`OffloadReport`](rustdoc:grit_lib::maintenance::OffloadReport) counts what moved and lists the config it set ([`OffloadConfigChange`](rustdoc:grit_lib::maintenance::OffloadConfigChange)). It also says whether the LOP can answer lazy fetches ([`LopReadiness`](rustdoc:grit_lib::maintenance::LopReadiness)) and whether `promisor.advertise` tells clients about it. Refusals are typed [`OffloadError`](rustdoc:grit_lib::maintenance::OffloadError)s inside `Error::Offload`. Running it again offloads blobs pushed since and folds objects pushed since into the promisor pack, even when no blob moves; it has nothing to do otherwise.

```rust
use grit_lib::maintenance::{offload_blobs, OffloadOptions};
use grit_lib::remote::partial_clone::ObjectFilterSpec;

let mut opts = OffloadOptions::new("lop", now_unix);
opts.filter = Some(ObjectFilterSpec::BlobLimit(1024 * 1024));
opts.configure_lop = true; // uploadpack.allowFilter + allowAnySHA1InWant in the LOP
let report = offload_blobs(&repo, &opts)?;
println!("moved {} blobs, main {} -> {} bytes",
    report.dropped_from_main, report.main_bytes_before, report.main_bytes_after);
```

### Dropping promised large blobs

A partial clone keeps every large blob it ever fetched. [`drop_promised_blobs`](rustdoc:grit_lib::maintenance::drop_promised_blobs) (also [`Repository::drop_promised_blobs`](rustdoc:grit_lib::repo::Repository)) removes the ones the promisor remote can supply again and nothing has needed recently, so they come back through the ordinary lazy fetch the next time something reads them. [`DropPromisedBlobsOptions`](rustdoc:grit_lib::maintenance::DropPromisedBlobsOptions) carries the size threshold (`blob:limit` semantics: at least `min_size` bytes), the recency cutoff and the current time, all passed in; [`DropPromisedBlobsOptions::from_config`](rustdoc:grit_lib::maintenance::DropPromisedBlobsOptions::from_config) reads `maintenance.drop-large-blobs.minSize` and `.expire`, and [`DropPromisedBlobsOptions::from_config_with_overrides`](rustdoc:grit_lib::maintenance::DropPromisedBlobsOptions::from_config_with_overrides) lets a caller's own size or [`DropExpiry`](rustdoc:grit_lib::maintenance::DropExpiry) (parsed from `never`, `now` or a date) take the place of either key, which is then not read. An `expire` that is not a date is [`ConfigError::InvalidDate`](rustdoc:grit_lib::error::ConfigError). [`drop_large_blobs_enabled`](rustdoc:grit_lib::maintenance::drop_large_blobs_enabled) says whether [`gc`](rustdoc:grit_lib::maintenance::gc) runs it as a phase ([`GcOptions::drop_large_blobs`](rustdoc:grit_lib::maintenance::GcOptions), [`GcStats::drop_large_blobs`](rustdoc:grit_lib::maintenance::GcStats)); `gc` checks that config before its first phase, and skips the phase ([`DropPromisedBlobsSkip::NoCurrentTime`](rustdoc:grit_lib::maintenance::DropPromisedBlobsSkip)) when `GcOptions::now_unix` is 0 rather than read a clock.

Only blobs stored in `.promisor` packs are candidates, and one is dropped only when it is stored nowhere else locally, no pack holding it has a `.keep` marker, some tree or tag in a promisor pack names it (so Git still treats it as promised once it is gone), no worktree's index (nor a `GIT_INDEX_FILE` one) or `HEAD` tree uses it, no commit a worktree's `HEAD` reflog named since the cutoff uses it, and no promisor pack holding it was written since the cutoff. The [`DropPromisedBlobsReport`](rustdoc:grit_lib::maintenance::DropPromisedBlobsReport) lists the dropped blobs ([`DroppedBlob`](rustdoc:grit_lib::maintenance::DroppedBlob)) and counts the rest by reason ([`KeptBlobCounts`](rustdoc:grit_lib::maintenance::KeptBlobCounts)). Deciding reads pack headers, the trees of the protected commits and, until every remaining candidate is found, the trees in promisor packs; it never fetches. Packs holding only dropped blobs are deleted and other affected packs rewritten, keeping their `.promisor` contents and modification time. Refusals are typed: [`Error::NoPromisorRemote`](rustdoc:grit_lib::error::Error), [`Error::OperationInProgress`](rustdoc:grit_lib::error::Error), [`Error::PreciousObjectsRepository`](rustdoc:grit_lib::error::Error) and [`Error::MaintenanceRunning`](rustdoc:grit_lib::error::Error); inside `gc` the first three become [`DropPromisedBlobsSkip`](rustdoc:grit_lib::maintenance::DropPromisedBlobsSkip) values instead.

```rust
use grit_lib::maintenance::{drop_promised_blobs, DropPromisedBlobsOptions};

let two_weeks_ago = now - time::Duration::weeks(2);
let opts = DropPromisedBlobsOptions::new(now, 1024 * 1024, Some(two_weeks_ago));
let report = drop_promised_blobs(&repo, &opts)?;
println!("dropped {} blobs, freed {} bytes ({} kept for a checkout)",
    report.dropped.len(), report.bytes_reclaimed, report.kept.checked_out);
```

Like Git's, fsck never fetches: a promised object that is missing stays missing, even with a promisor fetcher installed.

Partial-clone maintenance works offline. Repack keeps existing `.promisor` packs and their sidecars intact, and writes local objects into a separate unmarked pack. GC, reflog expiry, pruning, incremental repack, and dry runs honor promises without hydrating missing history. Missing non-promised objects still fail validation. Bitmaps are omitted when the local pack cannot contain the complete closure; `RepackStats::pack_path` and `pack_bytes` refer to the newly written local pack even when other packs remain.

The `grit` CLI maps fsck and hook failures to its own exit codes and messages; the library returns typed results only.

## Fsck diagnostic summaries

Call [`FsckReport::summary`](rustdoc:grit_lib::maintenance::repository_fsck::FsckReport::summary)
with the configuration, fsck options, and an `include_info` boolean to classify a
report for display. The returned
[`FsckSummary`](rustdoc:grit_lib::maintenance::repository_fsck::FsckSummary) keeps
all findings in discovery order as borrowed
[`FsckDiagnostic`](rustdoc:grit_lib::maintenance::repository_fsck::FsckDiagnostic)
values, each with its resolved severity and listing visibility. No objects are
read or changed by classification.

`summary.ok` is false if any finding has error severity. `summary.has_warnings`
records warnings independently of errors; visible informational findings do not
count as warnings. `include_info` changes visibility only. By default, most
informational findings are hidden, while `missingTaggerEntry` remains visible.
The CLI uses this policy for human listings and summary messages; JSON and
Markdown retain every finding, including hidden informational findings.

## Benchmarking

The October 2026 diagnostic-summary extraction was checked against main
`7cc7979535ce` and system Git 2.55.0 on a Linux factory VM with four AMD EPYC 7763
vCPUs, using Rust 1.99.0 and the `dist` profile. Builds and tests were idle during
measurement. Times below are median milliseconds.

| Repository and operation | Git | Grit before | Grit after |
| --- | ---: | ---: | ---: |
| 20,000 files, 50,000 commits: `fsck --no-dangling` | 267.38 | 221.36 | 221.76 |
| 1,001 warning trees and an informational tag finding: `fsck --no-dangling` | 23.75 | 15.72 | 15.37 |

The large-repository row uses 30 interleaved rounds with randomized tool order,
after three warmups per tool. Maximum process RSS was 60,960 KiB before and
60,724 KiB after, versus 28,444 KiB for Git. The diagnostic-heavy row uses
hyperfine with five warmups and at least 30 runs per tool; it exercises severity
and visibility classification rather than an empty report.

The standard `grit-bench fsck --warmup 3 --min-runs 10` scenario also ran on both
builds: 207.99 to 214.31 ms for grit, with Git at 265.00 and 261.92 ms respectively.
The subsequent interleaved comparison put grit's medians within 0.2%, with the
paired sample variability including no change. Summary classification performs
no additional object reads and resolves severity once per finding.
