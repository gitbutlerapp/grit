title: Network
summary: Remote dispatch, fetch, push, and ls-remote over every transport.

Network operations in grit-lib center on `Remote`: a typed URL (`RemoteUrl`), configured fetch refspecs, and one dispatcher for **fetch**, **push**, and **list refs**. Wire bytes still flow through the same fetch/push engines as before; `Remote` picks the transport from the URL scheme.

## Remote URL and config

| Scheme / form | `RemoteUrl` variant | Transport |
| --- | --- | --- |
| Path or `file://` | `Local` / `File` | [`fetch_local`](rustdoc:grit_lib::remote::transfer::fetch_local) / [`push_local`](rustdoc:grit_lib::remote::transfer::push_local) |
| `git://` | `Git` | [`GitDaemonTransport`](rustdoc:grit_lib::remote::transport::GitDaemonTransport) |
| `ssh://`, scp-style | `Ssh` | [`SshTransport`](rustdoc:grit_lib::remote::transport::SshTransport) (repo [`CommandRunner`](rustdoc:grit_lib::command_runner::CommandRunner)) |
| `http(s)://` | `Http` / `Https` | [`http_fetch`](rustdoc:grit_lib::remote::transport::http::http_fetch) / [`push_http`](rustdoc:grit_lib::remote::push::push_http) |

Parse a literal URL with [`RemoteUrl::try_from`](rustdoc:grit_lib::remote::RemoteUrl). Load `remote.<name>.url`, optional `pushurl`, and `fetch` refspecs (default `+refs/heads/*:refs/remotes/<name>/*`) via [`Remote::from_config`](rustdoc:grit_lib::remote::Remote). Config applies [`url_rewrite`](rustdoc:grit_lib::remote::url_rewrite) `insteadOf` / `pushInsteadOf` rules the same way Git does.

Local paths resolve through [`resolve_local_remote_git_dir`](rustdoc:grit_lib::remote::transport_path::resolve_local_remote_git_dir) from the repository root, not the process cwd.

A local or `file://` fetch or push copies the same objects the wire protocol would: those reachable from the requested refs that the receiver lacks. Other branches, hidden refs, excluded tags and unreachable leftovers stay behind even when they share a pack with what was asked for. When a source pack holds only objects the transfer must send, grit hard-links it instead of rebuilding it, and it builds a pack for the rest. The send set comes from the source's reachability bitmap when it has one. The one exception is a clone from a plain path (not a `file://` URL): like `git clone --local`, it links the source's packfiles as they are, unreachable objects included ([`FetchOptions::link_source_objects`](rustdoc:grit_lib::remote::transfer::FetchOptions::link_source_objects)).

To turn a user's repository argument (a configured name, a URL, an scp-style `host:path`, or a path) into a `Remote`, call [`resolve_remote_argument`](rustdoc:grit_lib::remote::fetch_request::resolve_remote_argument). A configured name wins. A name with a config section but no URL fails with `RemoteError::NoUrl`, and anything else fails with [`RemoteError::UnknownRemote`](rustdoc:grit_lib::remote::RemoteError). `grit fetch`, `grit pull` and `grit remote refs` all resolve their argument this way.

## Managing remotes

[`repo.remotes().configured()`](rustdoc:grit_lib::repo_handles::RepositoryRemotes::configured) lists every remote with a `remote.<name>.*` section, sorted by name, the same set `git remote` prints. Each [`ConfiguredRemote`](rustdoc:grit_lib::repo_handles::ConfiguredRemote) carries its URL, or `None` when the section has no URL, plus raw `push_urls`, `fetch_refspecs`, and effective fetch/push URLs after `url.*.insteadOf` / `pushInsteadOf`. [`list()`](rustdoc:grit_lib::repo_handles::RepositoryRemotes::list) returns only the names that have a URL.

[`repo.remotes().add(name, url)`](rustdoc:grit_lib::repo_handles::RepositoryRemotes::add) writes `remote.<name>.url` and the default fetch refspec to the shared repository config (also from a linked worktree), then reloads the repository's config. Like `git remote add`, it refuses an existing remote (`RemoteError::RemoteExists`) and a name whose tracking refs `refs/remotes/<name>/…` would be invalid (`RemoteError::InvalidRemoteName`), and it stores the URL as given.

[`repo.remotes().set_url(name, url, kind, dry_run)`](rustdoc:grit_lib::repo_handles::RepositoryRemotes::set_url) updates fetch or push URLs on an existing remote (`RemoteUrlKind::Fetch` or `Push`), returning [`UrlChange`](rustdoc:grit_lib::repo_handles::UrlChange). Push replaces every `pushurl` with one value. Returns [`RemoteError::UnknownRemote`](rustdoc:grit_lib::remote::RemoteError::UnknownRemote) when the section is missing.

[`repo.remotes().prune(name, dry_run, http_factory)`](rustdoc:grit_lib::repo_handles::RepositoryRemotes::prune) deletes stale remote-tracking refs without fetching, using the same stale-ref rules as fetch prune ([`tracking_refs_gone_on_remote`](rustdoc:grit_lib::remote::transfer::tracking_refs_gone_on_remote)). Returns the full ref names removed (or that would be removed when `dry_run` is true).

[`repo.remotes().set_head(name, mode, dry_run, http_factory)`](rustdoc:grit_lib::repo_handles::RepositoryRemotes::set_head) sets or deletes `refs/remotes/<name>/HEAD` via [`SetHead`](rustdoc:grit_lib::repo_handles::SetHead) (`Auto`, `Branch`, or `Delete`).

[`repo.remotes().inspect(name, options, http_factory)`](rustdoc:grit_lib::repo_handles::RepositoryRemotes::inspect) returns a [`RemoteSummary`](rustdoc:grit_lib::remote::RemoteSummary): fetch and push URLs, optional [`head_branch`](rustdoc:grit_lib::remote::RemoteSummary::head_branch), [`RemoteBranchState`](rustdoc:grit_lib::remote::RemoteBranchState) rows (`tracked`, `new`, or `stale`), and [`RemotePullBranch`](rustdoc:grit_lib::remote::RemotePullBranch) entries from `branch.*` config. With [`InspectOptions::query`](rustdoc:grit_lib::remote::InspectOptions::query) it lists refs on the remote (symrefs included) and compares them to local tracking refs; stale detection reuses [`tracking_refs_gone_on_remote`](rustdoc:grit_lib::remote::transfer::tracking_refs_gone_on_remote), the same rules as fetch prune. Without a query, branch names come from `refs/remotes/<name>/…` and are all reported as tracked.

## list refs

`Remote::list_refs` takes `ListRefsOptions` (prefixes, heads, tags, symrefs, peel) and returns `RemoteRef` entries in `git ls-remote` order. On disk it uses `list_refs_from_git_dir`. Over the wire it uses protocol v2 `ls-refs` when available, otherwise the v0/v1 ref advertisement.

With `peel` set, annotated tags come back as two entries, the tag and a `<tag>^{}` line holding the object it peels to: the first non-tag object, through any chain of tags of tags, as `git ls-remote` reports it. [`RemoteRef::peeled_tag`](rustdoc:grit_lib::remote::RemoteRef::peeled_tag) identifies those lines, and [`fold_peeled_refs`](rustdoc:grit_lib::remote::fold_peeled_refs) folds them into one [`PeeledRemoteRef`](rustdoc:grit_lib::remote::PeeledRemoteRef) per ref, with `peeled` set, keeping the listing order.

## Fetch and push

[`Remote::fetch`](rustdoc:grit_lib::remote::Remote) accepts [`FetchOptions`](rustdoc:grit_lib::remote::transfer::FetchOptions) and a [`Progress`](rustdoc:grit_lib::remote::fetch::Progress) sink; fetch negotiates protocol v2 when the server supports it. Negotiation offers every local branch, remote-tracking ref, tag and `HEAD` as a starting point and walks local history only as far as each round needs: 16 `have`s first, then twice as many per round, stopping as soon as the server is ready to send the pack. An incremental fetch whose new commits build on local history reads only the newest local commits, not the whole history. Its [`FetchOutcome`](rustdoc:grit_lib::remote::transfer::FetchOutcome) holds one `RefUpdate` per matched ref, including the ones that were already up to date. For a report, [`reported_updates`](rustdoc:grit_lib::remote::transfer::FetchOutcome::reported_updates) keeps the refs that changed or were refused, [`changed_ref_count`](rustdoc:grit_lib::remote::transfer::FetchOutcome::changed_ref_count) counts the changed ones, and [`has_rejections`](rustdoc:grit_lib::remote::transfer::FetchOutcome::has_rejections) says whether any update was refused (`UpdateMode::is_rejected`). `grit fetch` builds its output and exit code from these. [`Remote::push`](rustdoc:grit_lib::remote::Remote) uses [`PushRefSpec`](rustdoc:grit_lib::remote::transfer::PushRefSpec) and returns [`PushOutcome`](rustdoc:grit_lib::remote::transfer::PushOutcome). Before it sends anything, on every transport and for dry runs too, `Remote::push` runs the repository's `pre-push` hook through [`run_pre_push_hook`](rustdoc:grit_lib::command_runner::hooks::run_pre_push_hook) with one [`PrePushRef`](rustdoc:grit_lib::command_runner::hooks::PrePushRef) per update it would make; a hook that exits non-zero fails the push with `Error::Hook` (wrapped in `RemoteError::Library`) and leaves the remote untouched. Set [`PushOptions::no_verify`](rustdoc:grit_lib::remote::transfer::PushOptions::no_verify) to skip it. The lower-level `push_local` and `push_remote` never run `pre-push`. A local or `file://` push (including `push_local`) runs the remote repository's receive hooks (`pre-receive`, `update`, `post-receive`, `post-update`) the way [`receive_pack`](rustdoc:grit_lib::remote::serve::receive_pack) does, puts their output in [`PushOutcome::remote_messages`](rustdoc:grit_lib::remote::transfer::PushOutcome::remote_messages) and reports a declined update as `PushRefStatus::RemoteRejected`.

A push never holds its packfile in memory. [`write_pack_for_push`](rustdoc:grit_lib::objects::pack_objects::write_pack_for_push) streams the pack into the connection (ssh, `git://`) or, when the server advertises a resumable `pushBundle` endpoint, into the bundle file on disk. Over plain smart HTTP a receive-pack body larger than 1 MiB (Git's default `http.postBuffer`) is sent with chunked transfer encoding while the pack is still being written. A small probe request goes first so any authentication challenge is answered before the large body, as Git does. A custom [`HttpClient`](rustdoc:grit_lib::remote::transport::http::HttpClient) should override [`post_streaming`](rustdoc:grit_lib::remote::transport::http::HttpClient::post_streaming); the default buffers the body.

[`push_local`](rustdoc:grit_lib::remote::transfer::push_local) applies the same [`validate_ref_update`](rustdoc:grit_lib::remote::serve::validate_ref_update) checks as [`receive_pack`](rustdoc:grit_lib::remote::serve::receive_pack) (policy, hidden refs, fast-forward rules) before it copies objects or moves refs on a path remote.

To plan a push the way `grit push` does, start from its positionals: [`resolve_push_invocation`](rustdoc:grit_lib::remote::push_plan::resolve_push_invocation) splits `[<remote>] [<refspec>...]` into a [`PushInvocation`](rustdoc:grit_lib::remote::push_plan::PushInvocation) (configured remote, literal URL or path, or refspecs for the default remote). [`load_push_plan_context`](rustdoc:grit_lib::remote::push_plan::load_push_plan_context) reads the selected remote's refs ([`Remote::list_push_refs`](rustdoc:grit_lib::remote::Remote::list_push_refs), one scan of the push destination) into a [`PushPlanContext`](rustdoc:grit_lib::remote::push_plan::PushPlanContext), [`resolve_push`](rustdoc:grit_lib::remote::push_plan::resolve_push) turns a [`PushRequest`](rustdoc:grit_lib::remote::push_plan::PushRequest) into concrete ref updates, and [`open_push_destination`](rustdoc:grit_lib::remote::push_plan::open_push_destination) opens the `Remote` to send them to. Pass `PushPlanContext::remote_tips` on as `PushOptions::remote_ref_tips` so a local push does not scan the destination's refs a second time.

[`pull`](rustdoc:grit_lib::porcelain::pull::pull) is the high-level fetch-and-integrate operation. Build [`PullOptions`](rustdoc:grit_lib::porcelain::pull::PullOptions) (including shared [`FetchOptions`](rustdoc:grit_lib::remote::transfer::FetchOptions), explicit refspec/`FETCH_HEAD` integration, [`resolve_pull_autostash`](rustdoc:grit_lib::porcelain::pull::resolve_pull_autostash), and dry-run `--check` via [`PullCheck`](rustdoc:grit_lib::porcelain::pull::PullCheck)), pass a progress sink and HTTP client factory, and receive a typed [`PullOutcome`](rustdoc:grit_lib::porcelain::pull::PullOutcome). It maps `branch.<name>.merge` through the remote's fetch refspecs, uses [`resolve_pull_integration_base`](rustdoc:grit_lib::refs::branch_tracking::resolve_pull_integration_base) after explicit fetches, skips the fetch for a local `remote = .` upstream, and fast-forwards, merges, or adopts the upstream on an unborn branch. Failures are typed as [`PullError`](rustdoc:grit_lib::porcelain::pull::PullError); `grit pull` only builds options, invokes this API, and renders the outcome.

## Unreachable remotes

When the remote cannot be talked to at all, every operation (`list_refs`, `fetch`, `push`, [`clone`](rustdoc:grit_lib::remote::clone::clone), [`pull`](rustdoc:grit_lib::porcelain::pull::pull)) and every transport fails with the same [`Error::RemoteUnreadable`](rustdoc:grit_lib::error::Error::RemoteUnreadable). It carries the redacted URL or resolved path and a [`RemoteUnreadableReason`](rustdoc:grit_lib::error::RemoteUnreadableReason):

| Reason | When |
| --- | --- |
| `RepositoryNotFound` | A local path or `file://` URL that is missing or not a Git directory (valid `HEAD`, `objects/` and `refs/`, as Git checks). Listing refs never treats it as an empty remote. A linked worktree or `--separate-git-dir` checkout is followed through its `.git` file and works as a remote. |
| `Transport { detail }` | DNS, refused or reset connection, TLS, or timeout (HTTP and `git://`). Usually worth a retry. |
| `HttpStatus { status }` | A smart-HTTP error status such as 403, 404 or 5xx. A `401` challenge stays [`Error::Auth`](rustdoc:grit_lib::error::Error::Auth). |
| `NotGitServer { status, content_type }` | HTTP succeeded but the body was not a Git advertisement (for example `200 text/html` from a mistyped or parked host). |
| `NoHandshake` | The transport ran but never spoke Git, for example `ssh` failed to connect or a `git://` peer hung up without a ref advertisement. |

Wrapper errors answer the same question without unwrapping: [`Error::is_remote_unreadable`](rustdoc:grit_lib::error::Error::is_remote_unreadable), [`RemoteError::is_remote_unreadable`](rustdoc:grit_lib::remote::RemoteError::is_remote_unreadable), [`CloneError::is_remote_unreadable`](rustdoc:grit_lib::remote::clone::CloneError::is_remote_unreadable) and [`PullError::is_remote_unreadable`](rustdoc:grit_lib::porcelain::pull::PullError::is_remote_unreadable). The `grit` CLI maps all of them to exit code 128 and `kind: remote_unreadable` ([Exit codes](../exit-codes.md)).

HTTP remotes need an [`HttpClient`](rustdoc:grit_lib::remote::transport::http::HttpClient). Implement [`HttpClientFactory`](rustdoc:grit_lib::remote::HttpClientFactory) or, with the `http-ureq` feature, pass `None` to use the default ureq-backed factory (`UreqHttpClient` + [`HelperCredentialProvider`](rustdoc:grit_lib::remote::credentials::HelperCredentialProvider)). The `grit` binary on macOS enables `http-ureq-native-tls` (Secure Transport) for HTTPS throughput; other platforms use rustls unless you opt into `http-ureq-native-tls` when depending on `grit-lib`.

## Credentials and progress

[`HelperCredentialProvider`](rustdoc:grit_lib::remote::credentials::HelperCredentialProvider) satisfies HTTP `401` responses from configured `credential.helper` programs, then from the askpass program set with [`with_askpass`](rustdoc:grit_lib::remote::credentials::HelperCredentialProvider::with_askpass), and never opens a TTY. [`askpass_program`](rustdoc:grit_lib::remote::credentials::askpass_program) resolves that program the way Git does (`GIT_ASKPASS`, `core.askPass`, `SSH_ASKPASS`) from an [`Environment`](rustdoc:grit_lib::config::environment::Environment) you pass in; the default factory reads only `core.askPass` unless you build it with `DefaultHttpClientFactory::with_environment` (with the `http-ureq` feature). [`helpers_for`](rustdoc:grit_lib::remote::credentials::HelperCredentialProvider::helpers_for) lists the helpers it would run for a credential, so you can tell up front whether storing one would be a no-op. When neither the helpers nor askpass can supply a credential, `fill` returns [`Error::CredentialsUnavailable`](rustdoc:grit_lib::error::Error::CredentialsUnavailable) with the helpers it asked, and the transport reports [`AuthFailure::CredentialsUnavailable`](rustdoc:grit_lib::error::AuthFailure::CredentialsUnavailable) carrying the same list, so a caller can tell "no helper configured" from "the helper has nothing for this host". To save a user name and token a person gives you for any host, `approve` a credential built with [`ServerUrl::credential`](rustdoc:grit_lib::remote::grit_server_auth::ServerUrl::credential); `grit auth <url> --username … --token …` does exactly that.

Best-effort requests whose failure is ignored, such as the advertisement [`load_push_plan_context`](rustdoc:grit_lib::remote::push_plan::load_push_plan_context) reads and the bundle a clone tries first, use [`HttpClientFactory::create_for_probe`](rustdoc:grit_lib::remote::HttpClientFactory::create_for_probe): those clients never `reject` a refused credential, so the push or fetch that follows sends it, reports [`AuthFailure::Rejected`](rustdoc:grit_lib::error::AuthFailure::Rejected), and erases it as Git does. Every factory implements `create_for_probe`; one whose clients never reject (or carry no credentials) can return the same client as `create`.

After an authenticated retry, [`HelperCredentialProvider`](rustdoc:grit_lib::remote::credentials::HelperCredentialProvider) (and any custom [`CredentialProvider`](rustdoc:grit_lib::remote::credentials::CredentialProvider)) runs `reject` only when the server still answers `401`; a typo, missing repository, permission denial or server error (403, 404, 429, 5xx) leaves the stored credential untouched.

The HTTP client asks for credentials the way Git does: [`Credential::from_url`](rustdoc:grit_lib::remote::credentials::Credential::from_url) turns the repository URL into protocol and host, adding the repository path only when `credential.useHttpPath` applies, so a host-level entry from `git-credential-store` or a keychain helper serves every repository on the host. The full URL stays in [`Credential::url`](rustdoc:grit_lib::remote::credentials::Credential::url) for matching `credential.<url>.helper`, and `HelperCredentialProvider` never sends it to a helper. A `user:password@` in the URL fills the username and password (and is removed from `Credential::url`), so wrong URL credentials fail as [`AuthFailure::Rejected`](rustdoc:grit_lib::error::AuthFailure::Rejected).

To sign a user in to GitHub without a client secret, run the OAuth device flow with [`DeviceFlow`](rustdoc:grit_lib::remote::github_auth::DeviceFlow): [`request_device_code`](rustdoc:grit_lib::remote::github_auth::DeviceFlow::request_device_code) returns the user code to display, and [`wait_for_token`](rustdoc:grit_lib::remote::github_auth::DeviceFlow::wait_for_token) polls (through your `HttpClient` and an injectable [`PollClock`](rustdoc:grit_lib::remote::github_auth::PollClock)) until the user authorizes. Store the token with `approve(&github_token_credential(Some(&token)))` ([`github_token_credential`](rustdoc:grit_lib::remote::github_auth::github_token_credential)) and later HTTPS fetches and pushes to github.com send it as the password; `grit auth` is built on exactly this.

When formatting your own transport errors, strip embedded userinfo with [`redact_url_for_display`](rustdoc:grit_lib::remote::transport_path::redact_url_for_display) so passwords never reach logs or JSON. Pass [`NoProgress`](rustdoc:grit_lib::remote::fetch::NoProgress) to ignore sideband progress, or implement [`Progress::message`](rustdoc:grit_lib::remote::fetch::Progress) for side-band channel 2. Set [`FetchOptions`](rustdoc:grit_lib::remote::transfer::FetchOptions) `remote_progress` to omit `no-progress` on the wire so the remote may emit channel 2; decode chunks with [`SidebandLines`](rustdoc:grit_lib::remote::sideband_lines::SidebandLines) into [`RemoteLine`](rustdoc:grit_lib::remote::sideband_lines::RemoteLine) updates and lines.

Fetch and clone spool the received pack to a temp file and index it in place with [`ingest_received_pack_path`](rustdoc:grit_lib::objects::index_pack::ingest_received_pack_path), keeping the pack instead of exploding it into loose objects. Memory does not grow with the pack size. The sequential passes (trailer checksum and object scan) read through a memory map whose resident pages are dropped every few megabytes, and delta resolution reads each compressed object from the file. A thin pack (ref-deltas against objects the receiver already has, which Git servers send on incremental fetches) is completed the way `git index-pack --fix-thin` does it. The missing bases are appended to the file, the object count and trailing checksum are rewritten, and the pack and its `.idx` are named after the new checksum. On `git/git` (325 MB pack, 420k objects), indexing peaks at about 80 MB, against 63 MB for `git index-pack` on the same file.

A received pack's length in bytes is not known until it ends, so byte counts alone cannot say how far a transfer is. Return `true` from [`Progress::wants_received_objects`](rustdoc:grit_lib::remote::fetch::Progress::wants_received_objects) and the receive also counts the pack's objects on a background thread, reporting [`ReceivedObjects`](rustdoc:grit_lib::progress::ReceivedObjects) (received, total from the pack header, and deltas so far) through [`Progress::received_objects`](rustdoc:grit_lib::remote::fetch::Progress::received_objects). The counting never makes the receive wait; if it falls far behind a very fast transfer, it stops. The same counter is available on its own as [`PackStreamScanner`](rustdoc:grit_lib::objects::pack_stream_scan::PackStreamScanner). To turn the phases of a fetch or clone into one percentage and time-left figure, feed the same events to an [`OverallEstimator`](rustdoc:grit_lib::progress::OverallEstimator); it takes elapsed time as an argument rather than reading the clock.

## Serving fetches and pushes

The server side of the protocol lives in [`remote::serve`](rustdoc:grit_lib::remote::serve). [`upload_pack`](rustdoc:grit_lib::remote::serve::upload_pack) answers clones and fetches (protocol v0, v1 and v2) and returns an [`UploadOutcome`](rustdoc:grit_lib::remote::serve::UploadOutcome) with bytes sent, object count, negotiation rounds, and optional [`PackStats`](rustdoc:grit_lib::objects::pack_objects::PackStats). [`receive_pack`](rustdoc:grit_lib::remote::serve::receive_pack) accepts pushes. Both take an opened `Repository`, a reader and a writer, and [`ServeOptions`](rustdoc:grit_lib::remote::serve::ServeOptions), so the same code serves a pipe or ssh channel (the defaults) and smart HTTP (`advertise_refs` for `GET info/refs`, `stateless_rpc` for the POST). The library never reads the environment: map `GIT_PROTOCOL` with [`ProtocolVersion::from_git_protocol`](rustdoc:grit_lib::remote::serve::ProtocolVersion::from_git_protocol) at your process boundary. Open the repository with `RepositoryOptions::for_serving()`.

To stop a long fetch or push (client disconnect, deadline, quota), pass a [`Cancel`](rustdoc:grit_lib::progress::Cancel) to [`upload_pack_cancellable`](rustdoc:grit_lib::remote::serve::upload_pack_cancellable) or [`receive_pack_with_hook_cancellable`](rustdoc:grit_lib::remote::serve::receive_pack_with_hook_cancellable). A fired cancel returns [`ServeError::Cancelled`](rustdoc:grit_lib::remote::serve::ServeError::Cancelled) and does not move refs on receive-pack.

A protocol v2 `ls-refs` request asks the ref store for its `ref-prefix` ranges only, and reads objects only when the client sent `peel`. Even then, a fully peeled `packed-refs` answers without opening the tags. So the `ls-refs` call that every `git fetch` and `git ls-remote` sends costs in proportion to the refs it returns, not the refs stored. The v0/v1 advertisement always peels tags, and the push advertisement never does. Like Git, every advertisement includes refs whose objects are missing; such a ref just has no peeled value.

A pushed pack is streamed into a temp file in a quarantine object directory, so memory use does not grow with the pack size, and only bytes up to the pack's trailing checksum are read (a push client keeps its side open until it has the status report). Packs with fewer objects than `receive.unpackLimit` are stored as loose objects; larger ones are indexed and kept as a pack. `receive.maxInputSize` caps the pack size.

A push from a shallow clone starts its command list with a `shallow <oid>` line for each of the client's boundaries, and `receive_pack` accepts them anywhere before the flush. The parents of those commits are not required when the pushed objects are checked. When the repository's refs already reach the boundary (the usual case: a CI checkout cloned `--depth 1` from this server), the push is applied like any other. When accepting an update would make the repository shallow, it is refused with `RefUpdateRefusal::ShallowUpdateNotAllowed`, unless [`ReceivePolicy::shallow_update`](rustdoc:grit_lib::remote::serve::ReceivePolicy::shallow_update) (`receive.shallowUpdate`) is on. Then the new boundaries are added to the repository's `shallow` file before the ref is written, so `git fsck` accepts the result.

What a push may change is decided in three layers, in this order for each push:

1. [`ReceivePolicy`](rustdoc:grit_lib::remote::serve::ReceivePolicy), usually [`ReceivePolicy::from_config`](rustdoc:grit_lib::remote::serve::ReceivePolicy::from_config) (`receive.denyNonFastForwards`, `receive.denyDeletes`, `receive.denyCurrentBranch`, `receive.fsckObjects`, `receive.shallowUpdate`), plus the checks every server makes: valid ref names, hidden refs, the expected old value, and that the new objects exist.
2. An in-process [`ReceiveHook`](rustdoc:grit_lib::remote::serve::ReceiveHook) passed to [`receive_pack_with_hook`](rustdoc:grit_lib::remote::serve::receive_pack_with_hook). Its `pre_receive_ctx` and `update_ctx` methods take a [`ReceiveHookContext`](rustdoc:grit_lib::remote::serve::ReceiveHookContext) with the client's push options (the same values hook scripts see in `GIT_PUSH_OPTION_*`), so policy can refuse `-o` values before refs move. The default `pre_receive` / `update` methods ignore push options. `pre_receive_ctx` sees every accepted update and an object database that includes the still-quarantined pushed objects; refusing there refuses the whole push and nothing is moved into the repository. `update_ctx` checks one ref at a time after the objects are moved in. A closure `Fn(&RefCommand, &Odb) -> Result<(), RefUpdateRefusal>` is a `ReceiveHook` that implements `update`.
3. The repository's hook scripts (`pre-receive`, `update`, `post-receive`, `post-update`), run through the repository's `CommandRunner` with Git's environment (`GIT_DIR=.`, the quarantine variables and `GIT_PUSH_OPTION_*`). Each in-process check runs just before the matching script.

The [`ReceiveOutcome`](rustdoc:grit_lib::remote::serve::ReceiveOutcome) is typed: each [`RefUpdateResult`](rustdoc:grit_lib::remote::serve::RefUpdateResult) carries an `Option<RefUpdateRefusal>` ([`RefUpdateRefusal`](rustdoc:grit_lib::remote::serve::RefUpdateRefusal): `NonFastForward`, `StaleInfo`, `DeletionProhibited`, `PreReceiveHookDeclined`, `Policy(reason)` from your hook, ...), and `unpack_error` is an [`UnpackError`](rustdoc:grit_lib::remote::serve::UnpackError) (`Truncated`, `TooLarge`, `Malformed`, `Ingest`, `Rejected`, `FsckSkipList`, `Io`). Match on the variants; their `Display` text is what the client is sent on its `ng <ref> <reason>` and `unpack <reason>` status lines. Neither is an `Err`: `receive_pack` returns [`ServeError`](rustdoc:grit_lib::remote::serve::ServeError) only when the session itself fails (a malformed command list, a broken stream, or a repository error while applying the push).

Setting [`ReceivePolicy::fsck_objects`](rustdoc:grit_lib::remote::serve::ReceivePolicy::fsck_objects) to an [`ObjectFsckPolicy`](rustdoc:grit_lib::maintenance::fsck::ObjectFsckPolicy) (what `receive.fsckObjects` does) checks every pushed commit, tree and tag while it is still in quarantine. A malformed object refuses the whole push with [`UnpackError::Rejected`](rustdoc:grit_lib::remote::serve::UnpackError::Rejected), whose [`RejectedObject`](rustdoc:grit_lib::remote::serve::RejectedObject) names the object and its fsck message id; every update fails with `unpacker error` and the quarantine is deleted. Transfer checks are strict like Git's (warnings are errors); [`ObjectFsckPolicy::set_level`](rustdoc:grit_lib::maintenance::fsck::ObjectFsckPolicy::set_level) changes single messages, as `receive.fsck.<msg-id>` does in config.

```rust
use grit_lib::maintenance::fsck::{FsckMsgLevel, ObjectFsckPolicy};
use grit_lib::remote::serve::ReceivePolicy;

let mut fsck = ObjectFsckPolicy::default();
fsck.set_level("missingEmail", FsckMsgLevel::Warn);
let policy = ReceivePolicy {
    fsck_objects: Some(fsck),
    ..ReceivePolicy::default()
};
assert!(policy.fsck_objects.is_some());
```

To check objects from some other source with the same rules, call [`ObjectFsckPolicy::checker`](rustdoc:grit_lib::maintenance::fsck::ObjectFsckPolicy::checker) once and [`ObjectFsckChecker::check`](rustdoc:grit_lib::maintenance::fsck::ObjectFsckChecker::check) per object.

This server serves fetches, and refuses pushes to `refs/heads/protected/*` with a closure. Git runs it as `git push --receive-pack='guide_serve receive-pack' <path>` (and `--upload-pack='guide_serve upload-pack'` for clone and fetch):

## Partial clone and promisor fetch

Filtered fetch and clone record a promisor remote (`remote.<name>.promisor`, `extensions.partialclone`, and `remote.<name>.partialclonefilter`). Blobs omitted from the initial pack are **promised**: they appear in the object database as missing until fetched on demand.

Install a [`PromisorFetcher`](rustdoc:grit_lib::objects::promisor::PromisorFetcher) on [`RepositoryOptions::with_promisor_fetcher`](rustdoc:grit_lib::config::environment::RepositoryOptions::with_promisor_fetcher) (no global state). The default [`DefaultPromisorFetcher`](rustdoc:grit_lib::objects::promisor::DefaultPromisorFetcher) sends `want` lines for the missing object ids with `filter blob:none` (as Git does), does not update refs, and ingests the reply as a promisor pack. It asks the promisor remotes one after another in [`lazy_fetch_order`](rustdoc:grit_lib::objects::promisor_remote::lazy_fetch_order): config order with the `extensions.partialClone` remote last, each for what is still missing, moving on when one fails. A server refuses a whole request when it lacks one of the objects, so when a remote failed and several objects are still missing, the rest is split in halves that go through the remotes again: a large-object promisor that holds only the large blobs and `origin` holding the small ones serve one checkout between them. A remote that cannot be used at all (unreachable, no usable URL, authentication failed) is not asked again. When objects stay missing, the error is [`Error::PromisorFetchFailed`](rustdoc:grit_lib::error::Error::PromisorFetchFailed), naming each remote that failed with its first error, or [`Error::PromisedObjectMissing`](rustdoc:grit_lib::error::Error::PromisedObjectMissing) when every remote answered without the object. The `grit` CLI installs this fetcher for every opened repository.

When a fetcher is installed and [`fetch.promisorLazy`](rustdoc:grit_lib::objects::promisor::PROMISOR_LAZY_FETCH_CONFIG) is true (the default), an ODB read miss in a partial-clone repository triggers an isolated fetch (with recursion protection) and retries the read. With no fetcher, or when lazy fetch is disabled, reads return [`Error::PromisedObjectMissing`](rustdoc:grit_lib::error::Error::PromisedObjectMissing). Set `fetch.promisorLazy=false` in config, or `GRIT_NO_LAZY_FETCH=1` / `GIT_NO_LAZY_FETCH=1` in the environment, to opt out.

[`Repository::prefetch_promised`](rustdoc:grit_lib::repo::Repository::prefetch_promised) batch-fetches object ids before bulk reads. Tree-to-tree checkout (including clone checkout and [`grit switch`](../commands/switch.md)) collects missing blob oids from the diff and prefetches them in a single request when a fetcher is present. Hard reset also batches materialization and repair of unchanged paths, including an empty worktree/index after a metadata-only clone. Its batch includes required attribute blobs before attribute resolution, deduplicates shared blob ids, and excludes gitlinks and sparse-skipped paths that need no content. Files proven up to date by index stat data require no blob download. Repeating a reset after materialization uses the local objects and makes no data fetch.

[`CloneOptions::promisor_fetcher`](rustdoc:grit_lib::remote::clone::CloneOptions) carries the fetcher through to the opened repository so blobless clone checkout can prefetch without a separate reopen.

On the serving side, pass the client's [`ObjectFilter`](rustdoc:grit_lib::revwalk::rev_list::ObjectFilter) to [`write_upload_pack_stream`](rustdoc:grit_lib::objects::pack_objects::write_upload_pack_stream) (or [`build_pack_with_shallow_and_filter`](rustdoc:grit_lib::objects::pack_objects::build_pack_with_shallow_and_filter) for an in-memory pack). The filtered pack streams like an unfiltered one and holds the objects `git pack-objects --filter` selects: wanted objects and tag targets always, then the commits, trees and blobs the filter keeps.

### Large-object promisors

A server can point clients at the remotes that hold some of its objects, such as a large-object promisor (LOP) with the big blobs, through the protocol v2 `promisor-remote` capability. [`PromisorAdvertisement`](rustdoc:grit_lib::objects::promisor_remote::PromisorAdvertisement) models it: [`from_server_config`](rustdoc:grit_lib::objects::promisor_remote::PromisorAdvertisement::from_server_config) builds it from `promisor.advertise` and `promisor.sendFields`, and [`upload_pack`](rustdoc:grit_lib::remote::serve::upload_pack) advertises it and collects the names a client accepts in [`ServeOptions::accepted_promisor_remotes`](rustdoc:grit_lib::remote::serve::ServeOptions::accepted_promisor_remotes). `uploadpack.allowAnySHA1InWant` lets a LOP served by grit hand out blobs no ref points at.

On the client, a v2 fetch reads the advertisement and runs [`PromisorHandshake::evaluate`](rustdoc:grit_lib::objects::promisor_remote::PromisorHandshake::evaluate): [`PromisorAcceptPolicy`](rustdoc:grit_lib::objects::promisor_remote::PromisorAcceptPolicy) (`promisor.acceptFromServer`, `checkFields`, `storeFields`) decides, against the promisor remotes already in config ([`configured_promisor_remotes`](rustdoc:grit_lib::objects::promisor_remote::configured_promisor_remotes)), which advertised remotes to accept, and each verdict is a [`PromisorRejection`](rustdoc:grit_lib::objects::promisor_remote::PromisorRejection) or acceptance. Only a partial fetch accepts anything: one with a filter, or one from a remote configured as a promisor remote. The accepted names go back to the server with both the `ls-refs` and the `fetch` request, so a stateless smart-HTTP server sees them where it builds the pack. With [`FetchOptions::auto_filter`](rustdoc:grit_lib::remote::transfer::FetchOptions::auto_filter) the filter comes from the accepted remotes ([`PromisorDecision::combined_filter`](rustdoc:grit_lib::objects::promisor_remote::PromisorDecision::combined_filter)). The result is in [`FetchOutcome::promisor`](rustdoc:grit_lib::remote::transfer::FetchOutcome::promisor) and [`CloneOutcome::promisor`](rustdoc:grit_lib::remote::clone::CloneOutcome::promisor).

```rust
use grit_lib::remote::clone::{clone, CloneOptions};

let mut opts = CloneOptions::new("https://git.example.com/project.git", "project".into());
opts.auto_filter = true;
opts.config = vec![
    ("remote.lop.url".into(), "https://lop.example.com/project.git".into()),
    ("remote.lop.promisor".into(), "true".into()),
    ("promisor.acceptFromServer".into(), "knownUrl".into()),
];
let outcome = clone(opts, &mut progress, &cancel, None)?;
for remote in outcome.promisor.iter().flat_map(|h| h.decision.accepted()) {
    println!("accepted {}", remote.name);
}
```

Accepting never creates a remote, and lazy fetches use the URL configured locally, not the advertised one.

### Serving a repository whose large blobs live on a LOP

After [`offload_blobs`](rustdoc:grit_lib::maintenance::offload_blobs) (see [Maintenance](maintenance.md)), a server's large blobs live only on its LOP, and the rest of the repository sits in a `.promisor` pack. [`upload_pack`](rustdoc:grit_lib::remote::serve::upload_pack) serves such a repository by Git's rule. A client that accepted an advertised promisor remote gets packs without the promised blobs it lacks, and fetches those from the LOP. For any other client, the server either fetches them first or refuses with [`ServeError::ObjectMissing`](rustdoc:grit_lib::remote::serve::ServeError::ObjectMissing). That error carries a [`MissingObjectReason`](rustdoc:grit_lib::remote::serve::MissingObjectReason) and reaches the client as an `ERR` line before any pack data. Fetching first needs [`ServeOptions::lazy_fetch`](rustdoc:grit_lib::remote::serve::ServeOptions::lazy_fetch), or `uploadpack.lazyFetch` when it is `None`, plus a [`PromisorFetcher`](rustdoc:grit_lib::objects::promisor::PromisorFetcher) on the served repository. The library reads no environment: [`ServeOptions::lazy_fetch_from_environment`](rustdoc:grit_lib::remote::serve::ServeOptions::lazy_fetch_from_environment) maps `GIT_NO_LAZY_FETCH`, and [`ServeOptions::attach_promisor_fetcher`](rustdoc:grit_lib::remote::serve::ServeOptions::attach_promisor_fetcher) gives the opened repository a fetcher only when [`ServeOptions::lazy_fetch_enabled`](rustdoc:grit_lib::remote::serve::ServeOptions::lazy_fetch_enabled), and takes away any it was opened with otherwise, so a server without lazy fetch never fetches. Each fetch is planned again after a lazy fetch, so the client's filter still applies to the fetched blobs. [`receive_pack`](rustdoc:grit_lib::remote::serve::receive_pack) into such a repository accepts pushed trees that name promised blobs, as Git's connectivity check does. Repositories without promisor remotes keep the bitmap and pack-reuse fast path. Only these partial repositories plan their packs with the object walk, checking each blob is stored.

A local clone or fetch from a repository with promisor remotes of its own goes through the same in-process upload-pack instead of copying its object store, which would come up short.
